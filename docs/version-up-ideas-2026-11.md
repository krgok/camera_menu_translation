## 1. 食事制限プロファイル(アレルギー・ベジタリアン・ハラール等)と警告の強化
1. **何をするか**: 今の「苦手・アレルギー食材」自由入力を、家族ごとのプロファイル(例: 「甲殻類アレルギー」「ベジタリアン」「ハラール」「辛いのが苦手」)に拡張。プリセットのチェック+自由入力。スキャン結果の各項目に、色分けのバッジ(要注意/たぶん大丈夫/不明)と理由を表示。
2. **利用者のメリット**: 毎回入力しなくてよい。家族(子ども・高齢者・宗教上の制限のある人)ごとに切り替えられる。一覧で危ない料理がすぐ分かる。
3. **実現方法**: 既存の `avoid` を `profile` に置き換え、localStorage(または Supabase に `profiles` テーブル+RLS)に保存。プロンプトに「各項目について `risk: high|medium|low|unknown` と `reason`」を JSON スキーマで返させる(現在の `warning` の発展)。バッジは `ItemList` に追加。**「AI の推定です。重いアレルギーは必ずお店に確認」の注記は維持**し、注文フレーズ(#2)の「〇〇は入っていますか?」と連動させる。
4. **規模**: 中。
5. **リスクと費用**: AI の誤判定が健康被害につながり得る(免責の明記が必須。`unknown` を正直に出す)。API 費用は説明生成の出力が少し増える程度。DB を使う場合は新規テーブルのマイグレーションが必要。
6. **おすすめ順位**: 1位(安全性に直結し、家族の利用で価値が高い)。

## 2. 注文フレーズ集の拡充+店員に見せる画面
1. **何をするか**: 今は「これを1つください」の固定1文のみ。「辛くしないで」「パクチー抜きで」「テイクアウトで」「水をください」「会計をお願いします」「〇〇は入っていますか?」などを、タイ語を中心にテーブルで追加。画面を横向き・大文字で店員に見せる/読み上げる(現地語の TTS)。
2. **利用者のメリット**: 実際の注文で一番困る「カスタマイズ」と「アレルギーの確認」が、店員に伝わる。通信不要。
3. **実現方法**: `src/lib/orderPhrases.ts` のテーブルを複数フレーズに拡張(静的、無料、オフライン可)。`PointOrderModal` にフレーズ選択を追加。言語別の翻訳は人手で確認した文面にする(AI 生成の文面は、ネイティブ確認が望ましい。バンコク在住のご家族にレビューしてもらえる)。
4. **規模**: 小。
5. **リスクと費用**: 費用なし。誤訳のリスク(確認済みの文面だけを入れる)。TTS の音声は端末依存(タイ語の音声が無い端末あり → 画面表示を主にする)。
6. **おすすめ順位**: 2位(最小の工数で最大の実用性)。

## 3. PWA 化(ホーム画面に追加)+保存済みのオフライン閲覧
1. **何をするか**: ホーム画面にアイコンを追加してアプリのように起動。オフライン(機内モード・地下の店)でも、アプリ本体・保存済みの料理・指差し注文・履歴が見られる。
2. **利用者のメリット**: 起動が速く全画面で使える。電波が悪い店でも、保存した料理や注文フレーズを見せられる。
3. **実現方法**: `manifest.webmanifest`(アイコン・`display: standalone`)+Service Worker(アプリシェルのキャッシュ。ライブラリは追加せず手書き、または `vite-plugin-pwa`)。保存済み一覧は最後に取得した結果をキャッシュ(IndexedDB/localStorage)して、オフライン時に表示。`/api` はキャッシュしない(認証・課金のため)。点検で入れたオフライン表示バナーと相性が良い。
4. **規模**: 小〜中。
5. **リスクと費用**: Service Worker の古いキャッシュが更新を邪魔する(バージョン管理が必要)。iOS の PWA はカメラ・ログイン(OAuth のリダイレクト)の挙動に癖があるため、実機確認が必須。費用なし。
6. **おすすめ順位**: 3位。

## 4. 旅行ごとのアルバム、検索・並べ替え・書き出し
1. **何をするか**: 保存した料理を「旅行(例: 2026年12月 バンコク)」ごとにまとめ、料理名・原文・説明で検索、日付/お気に入り順に並べ替え。★(また食べたい/二度と食べない)の評価とメモ。旅行ごとに Markdown/テキスト/ZIP で書き出し(現在の履歴 ZIP 書き出しを保存データにも)。
2. **利用者のメリット**: 後から「あの店のあの料理」を探せる。旅の記録として残る。
3. **実現方法**: `saved_items` に `trip`(text)・`rating`(smallint)・`note`(text)列を追加するマイグレーション(`add column if not exists`、既存行はそのまま)+一覧 UI の拡張。書き出しは既存の `exportHistory.ts` / `exportText.ts` を流用。**DB 変更はユーザーが手動で実行**(005 のサイズ上限に新しい列の上限も追加)。
4. **規模**: 中。
5. **リスクと費用**: 保存形式の拡張(後方互換: 既存行は `trip` が空)。Supabase 無料枠(サムネイルは小さいため問題は小さい)。API 費用なし。
6. **おすすめ順位**: 4位。

## 5. 価格の自動認識の強化と、注文リストの合計(円換算)
1. **何をするか**: 現状は文字モードで価格(price/currency)を取り、「40 THB(約188円)」を表示。これを発展させ、複数の料理を「注文リスト」に入れて、数量・合計(円)・サービス料/VAT(タイは 7% や 10% が別表示のことが多い)を概算。メニューの価格が複数サイズ(S/M/L)のとき選択。
2. **利用者のメリット**: 予算の見通しが立つ。家族で分けるときの概算に使える。
3. **実現方法**: `MenuItem.price` を複数価格に拡張(Gemini のスキーマに `prices: [{label, value}]` を追加)、クライアントに注文リスト state(localStorage)、`currency.ts` の換算を流用。`/api/rates` は既に検証済み・CDN キャッシュ済み。
4. **規模**: 中。
5. **リスクと費用**: 価格の誤認識(「概算」と明記し、原価格を併記)。出力トークンが少し増える程度の API 費用。
6. **おすすめ順位**: 5位。

## 6. 多言語対応の強化(タイ語・中国語・韓国語・ベトナム語)と説明の質向上
1. **何をするか**: ①言語ごとの発音表記(タイ語は声調付きのローマ字、中国語はピンイン、韓国語は読み)を IPA に加えて表示 ②OCR に言語のヒント(`languageHints`)を渡して精度向上 ③説明に「日本の近い料理との比較」(例: 「日本の〇〇に近いが…」)と辛さの段階を追加 ④言語の自動判別が外れたときの手動指定。
2. **利用者のメリット**: 声に出して注文しやすい。味の想像がしやすい。読み取りミスが減る。
3. **実現方法**: Vision の `imageContext.languageHints` を設定(`vision.ts`)、プロンプトとスキーマに `romanization` と `compare_ja` を追加(出力は `sanitize.ts` の検証を通す)、`speech.ts` の言語コードを手動指定可能に。
4. **規模**: 中〜大(言語ごとの確認が必要)。
5. **リスクと費用**: 発音表記・比較の誤り(AI の推定である旨の表示)。出力が増えるため、1回あたりの費用がやや増える(`maxOutputTokens` の見直しが必要)。
6. **おすすめ順位**: 6位。

## 7. 利用残量の表示と運用ガード
1. **何をするか**: 「今日の残り: スキャン あと 32 回」を画面に表示。上限に近づいたら案内。管理者向けに、全体の使用量(今日何回・概算費用)を確認できる読み取り専用の仕組み。あわせて、Gemini モデルの更新(`gemini-2.5-flash` の提供終了に備え、モデル名を環境変数化し、新モデルの `thinkingConfig` 対応を確認)、Google のクォータ/予算アラートの設定手順書。
2. **利用者のメリット**: 突然「上限です」と言われず、残りを見ながら使える。費用事故と、モデル終了による突然の停止を防ぐ。
3. **実現方法**: 点検で入れた `menu_camera_api_usage` を読む RPC(本人の分だけ返す、`security definer`)を追加し、ヘッダーに残量を表示。モデル名は `process.env.GEMINI_MODEL`(既定は現行)に。
4. **規模**: 小。
5. **リスクと費用**: RPC の追加(DB 変更はユーザーが手動実行)。API 費用なし。
6. **おすすめ順位**: 7位(運用の安心のために、早めがよい)。

## 8. 同行者との共有(同じメニューへのコメント・投票)
1. **何をするか**: 家族でテーブルを囲んで、スキャンしたメニューの結果を共有リンクで見せ合い、「これ食べたい」に投票・コメント。注文リストを1つにまとめる。
2. **利用者のメリット**: 全員が自分のスマホで同じメニューの説明を読め、注文をまとめやすい。
3. **実現方法**: `shared_scans`・`votes` テーブル+RLS(メンバー制。共有リンクはランダムなトークン)、Supabase Realtime で同期。画像は共有しない(サムネイルのみ)か、共有時に明示的に確認。
4. **規模**: 大。
5. **リスクと費用**: **最もリスクが高い**: 共有データの RLS 設計の誤りは情報漏えいになる(他アプリと共有の DB のため特に注意)。メニュー写真に人が写る可能性。DB 負荷と無料枠。レビューとテストを手厚くしてから。
6. **おすすめ順位**: 8位(価値はあるが、規模とリスクが大きい。上の項目で土台ができてから)。
